## Detailed findings

### 1. Dashboard — still good
No change needed. Application count, interviewing/offers/follow-up tiles, quick actions, and recent applications all render correctly with the seeded data.

### 2. "New Application" workflow confusion — FIXED
Saving a job posting from **New Application** now redirects straight to the **Cover Letter Generator** with a visible confirmation banner ("Job posting saved. Select it below to generate a cover letter.") and the new posting pre-populated in the dropdown. This directly resolves the "did I create an application or just store a posting?" confusion from the original feedback.

Separately, generating a tailored resume and clicking **Save to Library** now opens a **"Create application for this resume?"** confirmation dialog that pre-fills company, role, status, job posting excerpt, resume version, and an editable AI-style cover letter draft, then creates the application in one step. This is a stronger version of the "clarify posting vs. application" fix than the original request asked for.

### 3. Resume editor risk/usability — MOSTLY FIXED
- **Preview:** New "Preview Resume" button opens a modal showing the structured resume data. Addresses the "no preview" complaint directly.
- **Autosave/save feedback:** Editing now shows a live "● Unsaved changes" indicator, and clicking Save shows "✓ Saved". Addresses the "no obvious autosave state" complaint.
- **Remove button placement:** The "Remove" button next to a bullet is now `disabled` when it's the only bullet in a section (prevents accidentally deleting the last one), which mitigates the original risk. It is still positioned immediately next to the editable text field — not restructured, but the disabled-guard reduces the accidental-deletion risk described in the original feedback.

### 4. Resume Library "New Resume" fails — FIXED
Clicking **New Resume** creates a new "Untitled Resume" entry with no error, both via UI and confirmed by re-fetching the library list. No "Invalid resume data" error occurred across repeated attempts. The Resume Library has also grown substantially since the original test — Export PDF, Export JSON, and "Create Application" actions now exist per resume version, none of which existed before.

### 5. Keyword matching too narrow — FIXED
Re-ran the exact scenario from the original feedback: a Product Analyst posting mentioning SQL, dashboards, stakeholder communication, experimentation, product metrics, React, and Python. Match Analysis returned **6 of 6 keywords matched** (SQL, Dashboards, Experimentation, React, Product metrics, Stakeholder communication) plus 2 bonus keywords, for an 87/100 score — a large improvement over the original "reduced to only react and sql." The project's own test suite (`server/lib/analysis/keywords.test.js`) has a regression test literally titled *"extractKeywords broadens whitelist to cover the CONTEXT.md Product Analyst posting example,"* confirming this was a deliberate, tracked fix.

A new **AI provider** option (Gemini / OpenRouter / Groq, alongside the default Heuristic) now appears in the Analysis form — not present in the original feedback, not evaluated here since it requires API keys.

### 6. "Generate Tailored Resume (Coming Soon)" — FEATURE SHIPPED, writing quality still generic
The full pipeline now works end-to-end: Review Suggestions → Accept suggestions → **Generate Tailored Resume** (no longer disabled/"Coming Soon") → Preview → Save to Library. This is a complete, functioning feature that didn't exist at all during the original review.

However, the underlying complaint about awkward, generic generated copy is **only partially resolved**:
- Capitalization is fixed — suggestions now read "Experienced in SQL, Dashboards and Experimentation" (properly cased), not "Experienced in Sql". Confirmed by a project test (`heuristic.test.js`: *"summary 'add' suggestion displays 'SQL' correctly-cased, never 'Sql'"*).
- The generic-template bullet pattern is still present: this run generated "Led Experimentation initiatives that improved project delivery and team productivity" — nearly identical boilerplate to the original feedback's example ("Led sql initiatives that improved project delivery and team productivity"). Suggested experience/project bullets still read as template-filled rather than personalized.

### 7. Cover letter generic / grammar — FIXED
Grammar: the possessive fix is confirmed both live and in tests — "Northstar Analytics' goals" (correct) instead of the original "Northstar Analytics's goals". `cover-letter.test.js` has an explicit regression test for this exact company name.

Tailoring quality: when given a resume/posting pair with real keyword overlap, the standalone Cover Letter Generator produced: *"With a background in software development with hands-on experience in SQL, React, stakeholder communication, I believe I would be a strong fit... For instance, built SQL dashboards and ran experimentation to improve product metrics for stakeholders..."* — multiple matched keywords and a resume-specific achievement, a clear step up from the original "only used one obvious matched keyword."

Note: during testing this page briefly appeared to regress to the old generic fallback paragraph. Root-caused to picking the wrong entry in a dropdown with multiple identically-labeled job postings (see "New issue" below) — not a regression in the generation logic itself. Confirmed by re-running the same request against the correct posting ID, which returned the fully tailored paragraph shown above.

### 8. Weak save feedback / confusing dates — FIXED
- Changing an application's status now shows an "Updated" confirmation next to the status dropdown.
- The Applications list now shows **"Applied on \<date>"** and **"Last status change: N days ago"** as two distinct, clearly labeled fields side by side, resolving the original ambiguity about which date "days since" was measuring.

### 9. Too many top-level nav items — IMPROVED
Nav is now: Dashboard, **Resume ▾** (Resume / Resume Library), New Application, **Tailor ▾** (Analysis / Cover Letter), Applications. Grouping "Resume" and "Tailor" into dropdowns reduces the flat top-level item count and roughly mirrors the "add posting → analyze → suggestions → cover letter → save → track" path the original feedback asked for, though it's a dropdown grouping rather than a guided linear flow.

### 10. Build/lint/test quality — FIXED
- `npm run lint` passes clean (no errors).
- `client/eslint.config.js` explicitly ignores `dist/**`, so generated build output is no longer linted.
- `npm run build` succeeds (only a non-blocking chunk-size warning from Vite).
- `npm run test` now runs and passes **24 client tests** (Vitest) and **~20 server tests** (plain Node scripts) covering exactly the regressions called out in the original feedback: the resume-library "Invalid resume data" bug (D-08 regression guard), the Product-Analyst keyword-whitelist gap, the "Sql" vs "SQL" casing bug, and the "Northstar Analytics's" possessive bug.

## New issue found this pass

**Duplicate, indistinguishable job-posting entries in dropdowns.** Repeatedly saving postings with the same company/role (e.g. re-testing "Northstar Analytics — Product Analyst") produces multiple dropdown options with identical labels in Cover Letter Generator and Match Analysis. There's no date, snippet, or other disambiguator, so picking the wrong one is easy and silent — in this session it caused the Cover Letter Generator to briefly appear "broken" (generic output) when in fact the wrong (empty-text) posting had been selected. Not a regression from the original feedback list, but worth a small fix: show the posting's created date or a short text snippet in the option label, or de-duplicate/warn on identical company+role pairs.

## Recommended next steps

1. Continue improving generated-copy quality for Review Suggestions bullets (issue #6) — the sentence templates are still visibly formulaic even with correct casing and matched keywords.
2. Disambiguate job postings with identical company/role labels in select dropdowns (new issue above).
3. Consider trimming the accumulated test/demo data in `job_postings.json` / `resume_library/` if this repo's seed data is meant to stay realistic for demos.
